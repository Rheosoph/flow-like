Use the widget action suite to investigate the time between a person-card click
and the resulting rental-history panel. The Criterion benchmarks further down
this page measure workflow execution and allocator behavior in isolation.

## Widget action measurements

The suite has two workloads. The application workload runs an exported app
through the web frontend, production API and executor routers, Postgres, Redis,
and a local S3-compatible object store. Its fixture keeps the workflow topology
and replaces database records with synthetic contacts and rental relationships.
The diagnostic workload runs a small database-filter, widget-instantiation, and
container-update graph with configurable transport delays.

Keep these boundaries separate when comparing results:

| Measurement | Boundary |
| --- | --- |
| Process readiness | Starting a local service until its readiness check succeeds |
| Page bootstrap | Document navigation until the configured person actions are available |
| History DOM | Click until the panel contains the selected person's expected history |
| Frame opportunity | Two animation frames after the verified DOM update; physical display paint is not measured |
| Action handler settled | The frontend handler returns, including work after the first UI update; this timing alone does not establish workflow success |

The browser alternates between people with distinct history markers and checks
the expected row count when configured. A stale table cannot satisfy the next
sample. Visibility checks cover CSS display and visibility; they do not establish
that every row is inside the viewport. Reports retain individual samples,
failures, configuration, and machine details. Use at least 100 samples per
scenario for tail-latency comparisons and repeat runs under the same background load.

The application fixture returns through its overview control between person
clicks. The reset UI, handler, and successful terminal event must arrive before
the next measured action. Reports retain reset timings separately from the rental-history round trip.
The optional browser `reset` configuration selects this control. Reset workflows
add load outside the timed history-click interval. Accounting callbacks after the
terminal event can still occupy an executor slot, as they do during normal use.

The application driver also verifies a successful terminal event in the invoke
stream. Matching rows followed by a failed workflow count as a failure.
Bootstrap must finish successfully before the first action; its earlier cards
DOM and frame timestamps remain separate from completion verification.
`requireTerminalSuccess: false` is an explicit mode for unverified browser probes.
Chrome DevTools Protocol stream observation, DOM observation, polling, and browser
automation add overhead; keep the same instrumentation when comparing revisions.

### Application workload

You need Docker Compose, Node.js, Bun, the installed workspace dependencies,
Rust, Python 3.11 or later, `uv`, `protoc`, OpenSSL, AWS CLI, and an authorized
metadata export of the investigation app. Keep exports outside the repository. The fixture builder
recognizes that app's existing page, event, widget, and board identifiers.
It removes credentials, external destinations, saved widget data, and comments
before importing source objects into the local stack.

The read-only exporter supports S3 directory buckets and downloads only current
source objects. It checks each object's ETag and writes a hash inventory:

```bash
python3 tests/widget-action-stack/export.py \
  --bucket "$WIDGET_BENCH_META_BUCKET" --app-id "$WIDGET_BENCH_APP_ID" \
  --region eu-west-1 --output /tmp/widget-app-export
```

Then prepare and run the local stack:

```bash
python3 tests/widget-action-stack/run.py prepare \
  --metadata-export /tmp/widget-app-export
python3 tests/widget-action-stack/run.py build
python3 tests/widget-action-stack/run.py benchmark
```

Preparation creates a separate Docker Compose project, local credentials, a
signed test session, and a synthetic Lance dataset. The build uses optimized
Rust and the real frontend's production static export. Web build products are
isolated from `apps/web/.next` and `apps/web/out`. The benchmark starts the
services, waits for readiness, navigates the actual Personen page, clicks the
configured person actions, then stops the processes it started.

The default database profile reproduces the inspected manifest's physical
shape: 47 live rows, 58 physical rows, 36 fragments, and three deletion files.
Arrow types, nullability, and primary-key metadata also match. Entity counts and
relationships are synthetic; the hosted table's customer records are not copied.
This preserves the cost of opening many small fragments that a compact fixture
would miss. For a controlled comparison with the same logical records in one
fragment, rerun preparation with the same export:

```bash
python3 tests/widget-action-stack/run.py prepare \
  --metadata-export /tmp/widget-app-export --fixture-layout compact
```

Stop the services before changing layouts and restart them afterward so cached
table handles cannot retain the previous dataset.

State, private service logs, fixture hashes, startup timings, and browser
results live in `/tmp/flow-widget-stack` by default. The generated
`fixture/browser-config.json` controls sample count, warmups, navigations,
concurrency, and semantic expectations. Use `concurrency: 1` for the isolated
reference, then repeat with `concurrency: 8` to send synchronized bursts from
independent headless browsers. Each browser performs the normal page bootstrap.
Start the service with `--executor-slots 8` to admit eight concurrent runs, or
keep fewer slots when measuring admission failures under overload.
`samples` is the planned action count per navigation across all workers. The
runner stops after a failed burst and retains partial results and failure counts,
including executor admission rejections. Initial and repeat navigation labels
describe document loads; neither label establishes that backend caches were cold.

To keep the services available for inspection:

```bash
python3 tests/widget-action-stack/run.py serve
# In another terminal:
python3 tests/widget-action-stack/run.py benchmark --existing \
  --output /tmp/widget-app-candidate
```

Compare two application runs with:

```bash
python3 tests/widget-action-stack/compare.py \
  /tmp/widget-app-baseline /tmp/widget-app-candidate
```

The comparison checks graph and record hashes, build profiles, browser versions,
concurrency, and instrumentation settings before calculating changes. Failed or
unverified actions remain failures. Changing the fragment layout is allowed when
the logical records match. `--allow-mismatch` shows incompatible runs side by side
without calculating a percentage improvement.

Use `serve --trace` for a separate diagnostic run with every API span sampled
and written to private service logs. Trace mode has extra overhead, so compare
it with another trace run. The run manifest records the instrumentation settings.
`--workers`, `--executor-slots`, and `--thread-stack-mb` control local runtime
capacity. The default 32 MiB thread stack accommodates the large graph in debug
builds; keep that setting fixed across comparisons.

Press Ctrl+C in the service terminal to stop its processes. To stop the isolated
infrastructure while retaining its data:

```bash
python3 tests/widget-action-stack/stack.py down
```

This path exercises the production authentication, authorization, page
bootstrap, prerun, quota, compilation, widget snapshot, HTTP dispatch, executor,
database, streaming, and browser rendering code. The local adapter supplies
the compute-accounting context normally supplied by Lambda. Its 2 GB accounting
metadata does not impose a memory limit on the process.
A pre-authenticated local OpenID Connect session exercises token verification;
interactive sign-in and an external identity provider are outside the measurement.

Local Postgres and RustFS do not reproduce DSQL network latency, Lambda
scheduling, or CDN behavior. Process readiness excludes periodic API
housekeeping workers. Use the same fixture and configuration across revisions,
and confirm the resulting change against hosted traces before claiming a hosted
latency target. The source export's hash and version also matter: a later draft
may execute a different graph from an earlier production trace.
The benchmark binary includes the standard and data node implementations used
by the entire Personen board. Other pages that require image, document, or AI
nodes need those catalog features added before they can be benchmarked.

### Diagnostic workload

Install the workspace dependencies, then start the optimized diagnostic server:

```bash
mise run bench:widgets:serve -- --profile local
```

In another terminal, run warm-cache, fresh-template-cache, and concurrent-burst
scenarios:

```bash
mise run bench:widgets -- --samples 100 --concurrency 8 \
  --output /tmp/widget-baseline.json
```

The four variants isolate serial accounting, overlapping accounting, bundled
widgets, and both changes together. The real executor template loader, accounting
client, widget source, LanceDB filter, and UI nodes execute in every variant.
The loopback hub supplies the accounting and widget endpoints. It does not run
the API's authentication, quota database, dispatch, or snapshot producer.

`--profile calibrated` on the server injects illustrative stage delays informed
by observed hosted requests. Those delays are inputs to the experiment, not a
measurement of AWS performance. Individual stages can be overridden with the
server's `--*-ms` options. The default `local` profile injects no delay.

The diagnostic `cold` scenario uses a new executor template-cache key. It leaves
the process, database connection, and OS page cache warm. Its dormant board nodes
exercise preparation cost; they do not reproduce the application's executed loops.

To compare a subsequent run and enforce a server-patch budget:

```bash
mise run bench:widgets -- --samples 100 --concurrency 8 \
  --compare /tmp/widget-baseline.json --output /tmp/widget-candidate.json \
  --budget-ms 500
```

This budget applies to receipt of the semantic history patch. Use the application
browser workload to evaluate the user-visible 500 ms target. Debug Rust builds
and a development frontend are useful for verifying the fixture, but their
latencies should not be presented as optimized application performance.

## In-process runtime benchmarks

<Aside type="caution" title="Benchmark numbers are not a service guarantee">
  The reference results below are a historical internal snapshot. They record
  the broad machine class, but not an exact CPU model, commit SHA, compiler
  version, power mode, or thermal state. Treat them as orientation and rerun
  the checked-in harness for decisions about current performance.
</Aside>

## What the harness measures

The throughput benchmark:

- loads the checked-in test app and board from `tests/flow`;
- initializes the current node catalog and local object stores;
- suppresses normal execution logs;
- warms the runtime before sampling;
- runs the same board concurrently at configured in-flight levels;
- reports Criterion latency and element-throughput distributions.

It measures in-process workflow execution. It does not include ingress,
external APIs, remote storage, model inference, databases, queueing, network
latency, container startup, or an end-user request path.

## Run the benchmarks

Run commands from the repository root.

<Tabs>
  <TabItem label="Throughput sweep">

```bash
FL_WORKER_THREADS=4 \
FL_CONCURRENCY_LIST="128,512,1024,2048,4096,8192" \
FL_MEASURE_SECS=10 \
RUST_LOG=off \
cargo bench -p flow-like-catalog \
  --bench throughput_bench \
  --features mimalloc \
  -- peak_throughput
```

  </TabItem>
  <TabItem label="Raw throughput">

```bash
FL_WORKER_THREADS=4 \
FL_MAX_IN_FLIGHT=32 \
RUST_LOG=off \
cargo bench -p flow-like-catalog \
  --bench throughput_bench \
  --features mimalloc \
  -- raw_throughput
```

  </TabItem>
  <TabItem label="Allocator comparison">

```bash
RUST_LOG=off cargo bench -p flow-like-catalog \

  -- --save-baseline system

RUST_LOG=off cargo bench -p flow-like-catalog \
  --bench allocator_bench \
  --features mimalloc \
```

The helper script runs both variants and formats their output:

## Configuration

| Environment variable | Default | Purpose |
| --- | --- | --- |
| `FL_BOARD_ID` | Checked-in benchmark board | Board loaded from the test app |
| `FL_START_ID` | Checked-in start node | Entry node executed by the benchmark |
| `FL_APP_ID` | Checked-in test app | App directory under the test store |
| `FL_TESTS_DIR` | `../../tests` from the package | Local benchmark object store |
| `FL_WORKER_THREADS` | Logical CPU count | Tokio runtime worker threads |
| `FL_MAX_BLOCKING_THREADS` | Worker threads × 4 | Tokio blocking-thread ceiling |
| `FL_CONCURRENCY_LIST` | Automatic sweep | Comma-separated in-flight levels |
| `FL_MAX_CONCURRENCY` | Logical CPU count × 8 | Maximum automatic sweep value |
| `FL_MEASURE_SECS` | `10` | Criterion measurement duration per level |
| `FL_MAX_IN_FLIGHT` | Logical CPU count × 4 | In-flight tasks in the raw benchmark |
| `RUST_LOG` | Inherited environment | Set to `off` for low-noise measurements |

## Make a comparison reproducible

Record these details with every result:

1. Commit SHA and whether the worktree is clean.
2. Rust and Cargo versions.
3. Operating system, kernel, CPU model, core topology, and memory.
4. Power mode, virtualization, and container limits.
5. Allocator and Cargo feature set.
6. Board, start node, app ID, and any changes to the test fixture.
7. Worker, blocking-thread, concurrency, and measurement settings.
8. Criterion estimate and confidence interval, not only the fastest sample.

Compare two commits on the same machine with the same fixture and environment.
Alternating baseline and candidate runs helps reveal thermal or background-load
drift.

## Interpret results

- **Single execution** isolates the overhead of one small in-process run.
- **Throughput** shows how efficiently the runtime uses concurrency.
- **Batch latency** grows with queue depth even while throughput improves.
- **Peak throughput** is not the same as a safe production operating point.
- **External-node workflows** require end-to-end benchmarks that include their
  actual dependencies.

Do not compare these numbers directly with another product unless the workload,
durability, logging, retries, isolation, hardware, and measurement boundary are
equivalent.

## Contributing a benchmark

1. Add or update a target under `packages/catalog/benches/`.
2. Keep the workload deterministic and check in its fixture.
3. Document the measurement boundary and environment variables.
4. Include before-and-after Criterion output for performance changes.
5. Explain any change in behavior, durability, or correctness that accompanies
   the performance result.
